# Цели AchieveTogether — первый рабочий вариант

**Область:** личные цели 0.6+; НЕ часть выпущенных 0.6.5 Mosaic и НЕ автоматический пункт 0.6.6. Реализованы в ветке `feature/goals-personal-v1`, публикация и проверка миграции требуют отдельного QA.

## Назначение
- Цель = желаемый результат; план = разовое действие; активность = повторяемое действие.
- `/goals` — список; `/goal/:goalId` — детали; `AddGoal` через существующий Blackout.
- В меню пользователя — «Цели», в создании — «Новая цель».
- Режимы `manual` (0..100), `metric` (числовой показатель с направлением от start к target), `milestones` (взвешенные этапы), `combined` (доля числового результата и этапов).
- Вес этапов по умолчанию 1, может редактироваться. Фактическое выполнение плана или активности НЕ меняет прогресс цели автоматически.
- Прогресс нормализуется до 0..100; 100% не меняет статус цели без явного подтверждения.
- Одно действие может быть привязано к нескольким целям. Удаление цели не удаляет план/активность.

## Сервер и данные
- Миграция: `database/goals_personal_20261123.sql` серверного репозитория.
- Таблицы: `goals`, `goal_milestones`, `goal_habit_links`, `goal_plan_links`, `goal_progress_events`.
- Включён RLS без публичных policies и REVOKE для anon/authenticated. Все маршруты `/goals*` идут через `authenticateUser`; чтение и изменение только при `owner_id=req.user.id`.
- GET /goals, POST /goals, GET/PATCH/DELETE /goals/:id, POST/PATCH/DELETE milestones, POST/DELETE links.
- Привязать можно только свою активность или собственный план. Чужие и совместные цели не открываются до отдельного этапа ACL/участников.
- История изменений доступна только владельцу. Совместные цели, интеграция поиска/чатов/Acc и realtime отложены.

## Принципы UI
Использовать существующие `RadioGroup`, `TA`, `CalendarInput`, `SelectList`, `Checkbox`, `Blackout`, `ConfirmAction`, RU/EN `common.goals`. SCSS отдельно в `scss/`. Не менять жесты SideMenu, оформление постов и логику планов.

## QA перед production
1. Применить миграцию до развертывания сервера и проверить таблицы/RLS/grants.
2. `npm test` на сервере и `npm run build` на клиенте, workflow на точных SHA.
3. Проверить личный CRUD, новые/пустые этапы, неравные веса, отрицательное направление метрики, 100%, режим combined.
4. Проверить чужой и анонимный доступ 401/404, подмену owner_id, добавление чужого плана/активности.
5. Проверить ошибки API, удаление ссылок и цели, работу на ПК/iPhone Safari, доступность модалки и клавиатуру.
6. Только после успешного QA считать функцию доступной пользователям.
