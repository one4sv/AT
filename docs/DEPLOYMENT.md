# Разработка и публикация AT

Текущая схема — облачные GitHub + Vercel + Render + Supabase. Локальный компьютер пользователя для работы с исходниками не требуется при наличии разрешённого доступа к этим сервисам.

Идентификаторы Vercel/Render/Supabase — инфраструктурные, а не замена секретов или прав доступа. Не публиковать API-ключи, сервисные роли, токены, пароли или файлы окружения.

## Клиент

- В текущем клиентском репозитории lockfile не хранится: локально использовать `npm install`. Если lockfile появится в будущих изменениях, предпочтительнее воспроизводимый `npm ci`; не утверждать наличие lockfile без проверки.
- Запуск: `npm run dev`.
- Продакшен-сборка: `npm run build` = `tsc -b && vite build`. `npm run lint` — ESLint.
- Маршруты: `src/App.tsx`. API-клиент `src/components/ts/api.ts` использует `/api/` и cookies. Проксирование/rewrites читать в `vercel.json`, не менять URL вслепую.
- Локализация `src/i18n/`, персонализация `src/theme-init.ts`/`SettingsContext`.
- UI-проверки описаны в [RELEASE_QA.md](RELEASE_QA.md).

## Сервер

- Основной код и маршруты — в backend-репозитории. В `package.json` стартовая команда `npm start`, Node ESM.
- Перед правками базы читать `utils/habitAccess.js`, роуты `routes/habits/`, `routes/chat/`, связанные RPC и миграции `database/*.sql`.
- Проверка синтаксиса: `node --check <changed-file>.js`. Для авто/компонентных тестов использовать существующие файлы/скрипты проекта, не заявлять отсутствующий test runner.
- В Render автодеплой привязан к `main`. После push ждать фактического результата и проверить, что `live` соответствует SHA коммита.
- Если изменён сервер и клиент, публиковать совместимые контракты; при необходимости сначала обеспечить обратную совместимость API.

## Supabase, миграции и безопасность

- Проверить схему таблиц, определения функций и ограничения RLS в подключённом проекте перед DDL. Миграции нужно читать и применять осознанно, а не запускать повторно.
- `service_role` и секретные ключи — только на сервере, никогда в Vite/React или README.
- Для доступа к данным проверять владельца/члена/роль, статус приглашения, блокировку и дату вступления, а не только UI.
- Изменения auth/RLS/SECURITY DEFINER — критические: запрет расширять публичные привилегии как временное исправление.
- Не трогать личные/продуктовые данные в целях теста без отдельного безопасного QA-сценария.

## Стандартный цикл

1. Получить свежий `main` обоих репозиториев; прочитать `AGENTS.md` и профильные MD.
2. Определить минимальный набор файлов и совместимость фронта/бэка.
3. Изменить код, проверить типы/синтаксис, локальные/доступные тесты.
4. Просмотреть diff, оформить один связный коммит по возможности, push в `main`.
5. Проверить SHA и результат автодеплоев, открыть production и проверить функцию под подходящим тестовым пользователем.
6. Записать подтверждённые изменения и оставшееся QA в Linear; документация рядом с кодом.

## Как трактовать статусы

`READY` на Vercel — сборка сайта прошла. `live` на Render — сервис запущен. Ни один статус не подтверждает, что пользователь может выполнить день в совместной активности, что изменённые роли защищены API или что iPhone отображает модалку правильно. Такие выводы возможны лишь по фактическому тесту.

Не сохранять конкретный SHA в постоянную инструкцию как «текущий»: он устаревает при следующем push. Ссылаться на `main` и проверять голову ветки каждый раз.


## Сверка документации с production

Не привязывать постоянные инструкции к одному SHA: сверять `main`, последний READY production-деплой Vercel и подтверждать ручной UI отдельно. Результат конкретной сверки 06.11.2026 находится в [DOCUMENTATION_AUDIT_2026-11-06.md](DOCUMENTATION_AUDIT_2026-11-06.md). После документационных коммитов production SHA может временно отставать.

Корневой `README.md` намеренно содержит **только ссылку** `https://achievetogether.vercel.app/` без команд запуска и технических ссылок. Рабочий индекс — [docs/README.md](README.md), инструкции ассистентам — [AGENTS.md](../AGENTS.md). Не возвращать в корневой README служебный текст при обновлении документации.

Если GitHub Actions прошёл, но production отстаёт по SHA, не называть результат опубликованным. Vercel может ограничить создание деплоев ошибкой `402/api-deployments-free-per-day`; дождаться восстановления лимита или решения владельца аккаунта, не менять тариф самостоятельно. Проверять `READY` и фактическую привязку production к коммиту; ошибка предыдущего деплоя не равна ошибке последнего CI.
