# Проверка приглашений в активность

1. В аккаунте отправителя откройте привычку → меню активности → «Добавить участников».
2. Выберите «Пригласить в активность», затем контакт и нижнюю кнопку «Сохранить».
3. В аккаунте получателя откройте **Чаты → личная переписка с отправителем**. В ней появится сообщение «Приглашение в активность», карточка привычки и кнопки «Принять» / «Отклонить».
4. Нажмите «Принять». Кнопки сменятся на «Приглашение принято», появится ссылка «Открыть активность», привычка добавится в список активностей получателя. У отправителя статус контакта станет «Участник» после обновления списка.
5. Для проверки отказа отправьте приглашение в другую привычку и нажмите «Отклонить». Привычка не добавится в список; карточка покажет «Приглашение отклонено».

Приглашение в активность не добавляет получателя в привязанную групповую беседу. Приглашение находится в личной переписке с тем, кто его отправил.

## Дополнительные проверки

- Повторное «Сохранить» для ожидающего приглашения не создаёт второе сообщение.
- Кнопки ответа видны только получателю. Отправитель видит «Ожидает ответа».
- После отказа можно пригласить повторно. Предыдущая карточка больше не принимает ответ.
- Если отменить приглашение крестиком у контакта, его карточка в чате становится недействительной.
- Запрет приглашений в настройках конфиденциальности возвращает ошибку отправителю; сообщение не создаётся.
- Выбранный контакт отображается над поиском, участник со статусом «Приглашён» — в оформлении активного контакта сайдменю.
- На ПК и телефоне список контактов занимает свободную высоту и прокручивается отдельно. Последние контакты и кнопка «Сохранить» доступны.

## Техническая проверка

Клиент: `npm run build`.

Миграция `database/habit_invitation_messages.sql` хранится в репозитории бэкенда и уже применена к Supabase проекта AT. Сообщение и ожидающее участие создаются одной транзакцией. Сервер проверяет получателя, права приглашающего, настройки конфиденциальности и актуальность сообщения.


## Ограничение пары и переход в беседу

- Активность **без беседы** допускает владельца и максимум одного другого человека. Ожидающее приглашение тоже занимает место; повторное приглашение тому же человеку не создаёт ещё одного участника.
- Когда второй человек уже принят или приглашён, действие прямого приглашения третьего скрыто, а сервер не позволяет его отправить даже прямым API-вызовом. Для расширения используется беседа.
- Владелец вправе добавить **одиночную** активность в существующую беседу либо создать новую, не приглашая предварительно пользователя в активность.
- «Добавить в существующую беседу» открывает список бесед. Если второй участник активности не состоит в выбранной беседе, сервер отправляет ему групповое приглашение **только при наличии у владельца соответствующего права и при разрешении приватности получателя**. При отказе в приглашении привязка не выполняется; если приглашение ожидает принятия, вступление происходит после согласия получателя.
- «Создать новую беседу» открывает **отдельную модалку только с полями названия, описания и аватара**. Второй участник существующей пары приглашается автоматически. Если второго ещё нет, беседа создаётся только с владельцем. Добавление третьего и следующих людей выполняется уже в беседе.
- В тестах отдельно проверьте: один участник → приглашение второго → запрет третьего; пару → существующая беседа (второй уже внутри / второй отсутствует / у владельца нет права приглашать / получатель запретил приглашения); пару → создание беседы; одиночную → создание беседы без контактов. После принятия приглашения в беседу проверьте сохранение доступа ко всем совместным данным.
- Миграция сервера `database/pair_only_habit_invitations_20261102.sql` уже применена в Supabase. Проверка разрешений новой беседы использует `deliver_group_invitations` через существующий серверный сервис. UI не заменяет серверную проверку.
