# Стиль кода и интерфейса AchieveTogether

Эта инструкция предназначена для разработчиков и ИИ-ассистентов. Применять при каждой правке AT вместе с docs/CONTINUE.md, [правилами dev 0.6.2](RELEASE_QA.md), [руководством по SCSS](SCSS_GUIDE.md) и [каталогом самописных компонентов](CUSTOM_COMPONENTS.md), [руководством по локализации](I18N.md) и [рисованным SVG](SVG_ART.md). Прямые указания пользователя имеют приоритет.

## Основное правило

Сохранять код и дизайн автора. Не менять названия классов, порядок импортов, структуру JSX, расположение логики и архитектуру ради собственного вкуса. Исправление должно затрагивать только связанную с задачей область. Не запускать форматирование всего файла или репозитория ради небольшой правки.

Явные требования автора: многострочный SCSS; относительные размеры страницы; существующие классы и общие компоненты; отсутствие новых form; сохранение пользовательских изменений. Остальные соглашения ниже — рабочие правила нового кода, выбранные по существующим файлам. Старые несовпадения не являются поводом для массового рефакторинга.

## Пробелы, отступы, переносы

- Один уровень вложенности — 4 пробела, без символов табуляции. Не смешивать табы и пробелы.
- В новом JS/TS/TSX использовать двойные кавычки и точку с запятой. Существующий стиль соседнего участка сохранять.
- Один пробел после запятой, после двоеточия, вокруг присваивания и бинарных операторов: const value = count + 1;.
- Перед открывающей фигурной скобкой пробел: if (ready) {, function Example {.
- Именованные импорты и объекты: { useState }, { editor, disabled }. Для нового state использовать принятый автором вид: const [ value, setValue ] = useState("");. Не переделывать соседние объявления только ради этих пробелов.
- Не выравнивать свойства дополнительными пробелами «колонками». Не оставлять пробелы в конце строк.
- Логические группы отделять одной пустой строкой; не вставлять пустую строку после каждого выражения.
- Короткое понятное выражение можно оставить на одной строке. Длинные вызовы, объекты, условия и JSX разбивать по смыслу. Жёсткий лимит длины строки автором не установлен.
- Не сворачивать несколько действий, обработчик или ветки условия в одну строку.
- Кодировка UTF-8, русские строки без повреждения символов, перевод строки в конце файла. При небольших правках сохранять окончания строк файла.

## React / TypeScript / JSX

Существующий порядок импортов сохранять. Новые импорты добавлять к подходящей группе, без автоматической пересортировки. Компоненты и типы — PascalCase, функции и локальные переменные — camelCase. Имена классов, полей API и базы не переименовывать: их написание является контрактом.

Несколько props или длинный обработчик — каждый prop на отдельной строке. Закрывающий > или /> на отдельной строке. Простые элементы без длинных props могут оставаться однострочными. Не менять оформление всего JSX ради одного нового свойства.

```tsx
const [ saving, setSaving ] = useState(false);

return (
    <button
        type="button"
        className="habitCollaborationButton"
        disabled={saving}
        onClick={openSettings}
    >
        <GearIcon />
        <span>{t("settings.title")}</span>
    </button>
);
```

Hooks не вызывать условно и после условного return, если из-за него меняется порядок вызовов. Cleanup эффекта возвращает void, а не boolean от delete. Явно учитывать null и union-типы, не скрывать проблему через any или необоснованный as.

Использовать существующую локализацию, а не выражения вида en ? "..." : "...". Не добавлять form без отдельной задачи. Кнопкам указывать type="button", иконкам-кнопкам доступное имя. При блокировке действия проверять право на сервере; disabled в интерфейсе сам по себе не защищает API.

Если пользователь просит файл в ответе — отдавать полный рабочий файл, а не набор несвязанных фрагментов.

## SCSS

Каждый селектор и каждая декларация на отдельных строках. Пробел перед { и после :, точка с запятой после свойства. Вложенные селекторы и @media также всегда многострочные. Не писать a { color: ...; padding: ...; }.

Сначала основные свойства блока, затем состояния/дочерние элементы, затем адаптивные изменения. Если в файле уже принята другая группировка, сохранить её. Держать связанные стили в существующем SCSS страницы или компонента.

```scss
@use "../../../scss/mixins" as var;

.settingsPage {
    width: 50%;
    flex-shrink: 0;
    display: flex;
    flex-direction: column;
    height: 100%;
    overflow: hidden;
    padding-top: 6dvh;

    @media (max-width: 800px) {
        padding-top: 0;
    }
}
```

Не создавать параллельный набор почти одинаковых селекторов и не повышать специфичность без причины. Перед новым правилом найти существующее. Не применять !important как обычный способ исправления вёрстки.

## Единицы измерения

- Новые фиксированные размеры ширины/высоты интерфейса задавать через vw и vh/dvh. Для доступной высоты мобильного экрана предпочтителен dvh.
- Проценты допустимы для размеров относительно родителя: width: 100%, height: 100%, width: 50%.
- auto, flex, grid, min-height: 0 и min-width: 0 предпочтительнее искусственно вычисленной высоты.
- Отступы и промежутки масштабировать через vh/dvh и vw по образцу соседних компонентов.
- Не измерять геометрию страницы в px и не вводить большие фиксированные пиксельные ширины/высоты.
- Не путать это с существующими токенами: тонкая рамка 1px, скругление 24px, breakpoint 800px, blur и размеры шрифта уже есть в проекте. Не переводить их механически во viewport-единицы. Это не новые размеры контейнеров.
- Нулю единица не нужна: margin: 0.
- Не вычислять размеры через JS, если задачу решают flex/grid/CSS. Измерения DOM допустимы для клавиатуры, composer или жестов, когда это действительно необходимо.

## Переменные, миксины, темы

SCSS-переменная $name вычисляется при сборке. CSS-переменная var(--name) меняется во время работы приложения и нужна для тем, акцента и персонализации. Не заменять динамический цвет темы фиксированным hex или SCSS-константой.

Переиспользовать src/scss/_variables.scss и src/scss/_mixins.scss. Пути @use зависят от расположения файла. Для миксинов в проекте используется namespace var: @include var.centerModal;.

Стандартный SCSS-токен границы:
```scss
$block_border: color-mix(in srgb, var(--borderWh) 22%, transparent);
```

$block_border и var(--block_border) — разные сущности. Нельзя предполагать наличие CSS-переменной по имени SCSS-переменной. Проверить её объявление и экспорт; при необходимости импортировать SCSS-токен через соответствующий namespace. Не ссылаться на неопределённую переменную.

Основные существующие CSS-токены: --bgc, --tc, --mc, --interact, --borderWh, --borderHabit, --accent, --accent_text, --grad, --inner_text, --menuButtHover, --blur. Проверять назначение по актуальному файлу темы. Не дублировать их новыми почти одинаковыми названиями.

Для стеклянной поверхности:
```scss
background-color: var(--mc);
backdrop-filter: blur(var(--blur));
-webkit-backdrop-filter: blur(var(--blur));
```

Не добавлять вложенную непрозрачную поверхность поверх blur, если она полностью скрывает эффект. Проверять контекст наложения, overflow и клики. Не фиксировать оранжевый/фиолетовый: градиент действия использует --accent и --grad.

### Обязательные правила акцентов и удалений

Акцентные элементы `--accent` / `--accent_text` не должны висеть на голом фоне сайта или единственном слое `--mc`. Добавлять вложенную контрастную поверхность `--interact` (стандартный список/контрол), затем помещать на неё акцентные SVG/текст. Не подменять вложенный фон прозрачностью.

Все удаления/выходы/опасные действия оформлять аналогично `.SMaccountButt.logout`: `--notValid`, рамка `1px solid var(--notValid)`, при hover/active — `--notValidBg`. Не оформлять удаление как обычную акцентную кнопку. Для быстрого действия удаление — `.quickActionRemove`; перенос — только за отдельную ручку с `ListIcon` цвета `--borderWh`, включая iPhone touch.

## Дизайн

- Сохранять существующий визуальный язык: округлые поверхности, тонкие границы, акцентные SVG, персонализируемый градиент и glass.
- Главные действия — градиент; круглые Back/Close и иконки — по существующим компонентам. Текст кнопок визуально центрировать.
- Стандартное скругление крупных блоков — существующие 24px; форму нижнего мобильного листа брать из соседних модалок.
- Общую рамку блока не дублировать на каждом вложенном div. Для input/button применять предусмотренные для них рамки.
- Активный контакт оформлять общим contact-компонентом и active, как в SideMenu. Не заменять готовую карточку строкой имени.
- Использовать общие RadioGroup, ContextMenu, модалки/Blackout, composer и просмотр изображений imgPrev. Не делать второй несовместимый вариант.
- Контекстное меню по кнопке, ПКМ и долгому нажатию должно содержать одинаковые действия. Удаление требует предусмотренного подтверждения.
- Декоративные SVG не должны выходить за границы, перекрывать текст и перехватывать pointer events. Не увеличивать верхние декоративные блоки так, чтобы они вытесняли содержимое.
- Компактный межстрочный интервал близко к браузерному; не добавлять большие промежутки между строками и абзацами поста без причины.
- Обычный текст переносить по словам; для непрерывной длинной ссылки допустим overflow-wrap: anywhere. Не ставить word-break: break-all на весь интерфейс. Имена в узкой строке — min-width: 0, ellipsis и nowrap по месту.

## Мобильная вёрстка и жесты

Flex-список занимает свободную высоту через flex: 1 и min-height: 0; скролл находится на списке. Не оставлять большую пустую нижнюю прокладку и не создавать вложенный оверскролл. Учитывать safe-area и экранную клавиатуру. Проверять реальный iPhone/Safari: dev mobile mode на ПК недостаточно.

Меню, горизонтальный слайдер и сворачивание не должны обрабатывать один жест одновременно. Сохранять арбитраж dontHandle/dontHandleOther; сбрасывать захват на end/cancel. Свайп вправо закрывает меню активности. Не менять существующие пороги и длительности без задачи.

Общий long-press: удержание 350 ms открывает меню **до** отпускания; отпускание на исходном элементе оставляет меню открытым, на пункте выполняет действие, вне обоих отменяет. Hover-стили ограничивать @media (hover: hover), мобильное нажатие — @media (hover: none). Сохранять focus-visible для клавиатуры.

## Проверка и публикация

Проверить изменённый сценарий на desktop и mobile: длинный текст, пустой список, загрузка, ошибка, права владельца/участника/постороннего, открытие/закрытие меню и модалок. Загрузка участников — скелетон. Не маскировать ошибку пустым состоянием.

После TSX-правок запускать npm run build; для сервера — проверку синтаксиса и связанные API/права. Тестировать поведение, а не копию реализации. Документация сама по себе сборки не требует.

Прямые коммиты в GitHub разрешены в этой работе. Объединять готовые изменения в один коммит на репозиторий за выпуск из-за лимита деплоев Vercel. После изменения кода проверить SHA и статус Vercel/Render. Не делать лишний ручной деплой поверх автодеплоя. Не коммитить секреты, .env, node_modules, сборки и тестовые логи. Постоянные QA-аккаунты и данные не удалять.

## Проверка заимствованных компонентов и CSS (обязательна)

Перед созданием или изменением интерфейса найди **определения и использование** всех переиспользуемых компонентов и CSS-классов: JSX, исходный SCSS, миксины, наследуемые правила, медиа-запросы, базовый контейнер, `Blackout` и готовые аналоги на соседних экранах. Особенно учитывай, что `@include var.centerModal` задаёт `left`/`transform` и что мобильный `.mobileBar` рендерится в обёртке `.blackoutModule`, отдельно от содержимого. Недостаточно посмотреть только файл нового компонента.

**Контрольный список перед коммитом интерфейса:** полный размер мобильной модалки (без `max-width: 94vw` и отступов от экрана), позиция полоски свайпа относительно окна, отсутствие лишних кнопок закрытия, сохранение скролла внутри списка, расположение поиска и SVG, поля `padding-inline-start`/`padding-inline-end`, `focus-visible`, safe-area, клавиатура iPhone и положение нижних кнопок. Не исправляй общие компоненты ради одного окна, если можно ограничиться его существующим классом.

**Цветные поверхности:** если активный контакт или кнопка уже имеет акцентный/градиентный фон, не накладывай на него бордер с альфой. Полупрозрачный бордер смешивается с фоном и оставляет некорректные края. Для `.contactsUser.active` и градиентных подтверждений используй `border: none`; нейтральные стеклянные блоки могут сохранять штатную обводку. Проверяй итоговую специфичность вложенных селекторов, а не только новое правило.

В совместных активностях используй штатные `Blackout`, `HabitParticipantPicker`, `HabitCollaborationSettings` и `contactsUser.active`. Не добавляй отдельные подтверждения, самостоятельные оверлеи или другой вариант списка контактов. Прежде чем повторять существующий стиль, найди его исходное определение, в том числе `src/scss/modules/CreateChat.scss` для `.createChatSearch`.

Для мобильных и десктопных окон совместных активностей сравнивать реальную ширину с `CreateChat` (`src/scss/modules/CreateChat.scss`): на ПК компактная ширина `25vw`, на мобильном — `100%`. Выбор участников — существующие мини-карточки `createChatChosenCons` над поиском, включая режим создания беседы. Одиночную активность владелец вправе сразу привязать к беседе, без предварительных приглашений. У переиспользуемых карточек контактов внутри активности не добавлять `outline` при hover/active: появляется лишний пиксель по краю.

**Типографика:** не добавлять и не переопределять `font-weight` при правках интерфейса AT. Сохранять штатную жирность текста из существующих компонентов и глобальных стилей; без прямого требования не вводить собственные значения.

## Локализация и постоянные строки

- Текущая схема: i18next, namespaces `common/sign/info/settings/acc`; локали в `src/i18n/locales/ru` и `en`. Изменять **оба JSON** в одном коммите и проверять ключи.
- Новые видимые строки выводить через `useTranslation("<namespace>")`, а не через inline `en ? "..." : "..."`; для внутренних ссылок — React Router `Link`, без HTML внутри переводов. Исключение для моделей данных `RoadmapText` описано в [I18N.md](I18N.md).
- В языковом интерфейсе `/settings/language` значения `ru/en` хранятся в `settings_lang`. Не создавать второй независимый источник языка.
- Термины API, идентификаторы, роли и значения настроек (`personal`, `shared`, `owner`) остаются машинными ключами, переводу подлежит только подпись.
- Перевод может быть неполным: при добавлении новой страницы документировать, какие части пока ещё заданы на одном языке.

## Жесты и состояния меню

Любой `data-context-menu`: таймер 350 мс открывает **до отпускания**; `pointermove` подсвечивает пункт, `pointerup` на пункте выполняет, на исходном элементе оставляет меню открытым, вне обеих зон закрывает. Меню между собой не переключаются, кроме явно связанных триггеров в одном хедере. Открытие после `pointerup` — ошибка.

При вложенном скролле модалки жест вниз не должен закрывать `Blackout`, если `scrollTop > 2` у прокручиваемой области на `touchstart`.

Бордер на активной градиентной поверхности запрещён. `smHeaderSelected.open`, `SMnavActive` и другие состояния с `linear-gradient(var(--accent), var(--grad))` должны иметь `border: none`. Иконки `ContextMenuButt` и `SMnav` используют акцентный цвет, действия удаления — `notValid`.

## Обязательные требования для новых UI

## Selector и изоляция касаний (регрессия iOS)

Не создавать собственные сегментированные переключатели. Штатный `Selector` сразу реагирует на `pointerdown`, ведёт индикатор на `pointermove`, вызывает колбэк при `pointerup`; `pointercancel` отменяет. `setPointerCapture`, `touch-action:none`, `stopPropagation` для всех касаний обязательны. Избегать `dontHandleOther` как условия доступа к самому селектору: он не является индикатором заблокированности модалки. Свайп SM не имеет права начинаться под `ContextMenu`/`Blackout`.

## Расписание активности: архив, недели, прозрачность

`Schedule` не должен скрывать все дни архивной активности только из-за `!habit.ongoing`; архивное расписание доступно для просмотра, **не для редактирования**. Если в дне есть сохранённый schedule block, показывать его даже при отсутствии этого дня в `chosen_days`.

Блоки показываются независимо от `isOddWeek`, когда настройка `schedule_settings[habitId].isSeparated` выключена. Проверка чётности допустима только при `isSeparated=true`; если в текущей чётности нет дополнительных блоков, показывать обычную информацию активности, а не пустую карточку.

Для `.scheduleDiv` использовать `background-color: var(--mc)`, `backdrop-filter: blur(var(--blur))` с `-webkit-backdrop-filter`, сохраняя border только на внешнем контейнере, под которым виден фон сайта.

### Обои, графика и предпросмотр

**значения LineBar и скорость фоновых сцен**

- Подпись `SeekBar` / LineBar должна содержать **только название настройки**, без текущего числа рядом. Значение с единицей измерения появляется **только внутри ползунка** (текущее при перетаскивании / значение при наведении), по образцу «Степень размытия».
- У «Размытие заднего фона» `unit="px"`, у «Скорость анимации» `unit="×"`; диапазон скорости **0–3×**, шаг 0.25. При 0× анимация остановлена, деления на ноль в длительности нет. Серверное API допускает 0.
- Из сцены «Ретро-шоссе» полностью убрана машина. Дорога, закат и анимация дорожных полос остаются.

**мгновенное оформление фона без статичного кадра**

- `settings_bg_effects` хранит весь `BackgroundEffects` (размытие, movement, filter, speed) через штатный `useLocalStorage`, а не `useState` с пустыми значениями.
- Ключ включён в `APPEARANCE_KEYS`: последнее оформление продублировано в `settings_appearance` и доступно до получения пользователя, как accent/grad/bg. Пользовательский ключ `<nick>_settings_bg_effects` отделяет настройки разных аккаунтов.
- Сначала рисуется значение из localStorage; запрос `settings` не должен заменять актуальный локальный кэш устаревшим ответом. Сервер используется для первичной гидратации, когда локального значения нет. `refetchSettings` не должен возвращать фон к дефолтным значениям.
- При первом входе без локального кэша `Background` не рисует промежуточный статичный кадр: ждёт завершения загрузки настроек; при последующих открытиях локальный кэш применяется уже при первом React render.
- Изменение ползунка, фильтра или переключателя мгновенно меняет `bgEffects` в контексте, перерисовывает фон и сохраняется в localStorage; отправка на сервер остаётся с debounce. Проверить reload, медленный сервер, смену аккаунта, ошибку API и 0×.

**предпросмотр фоновых сцен, паттерны, переключение движения**

- В `BackgroundLibrary` выбор **не** включает `bg_effects.movement` автоматически. Движение включается/выключается только через отдельный `Toggler`; у статичных фонов он передаёт `disable={!supportsBackgroundMotion(bg)}`, визуально сереет, а `SeekBar` скорости тоже заблокирован. Никаких фоновых запросов `updatesettings` при простом выборе стандартного фона.
- Рядом с именем стандартного фона показываются компактные SVG-иконки возможностей с `title` на обёртке: `Film` — анимация доступна, `Palette` — цвета фона зависят от темы. Не ставить `title` прямо на Lucide-SVG (TypeScript не поддерживает этот prop).
- Для `color` сплошной фон **обязательно** рендерится внутренним `.backgroundCanvas` с `var(--bgc)` и эффектом `getBackgroundFilter`, иначе фильтр `invert` («Негатив») не работает.
- Контурные фигуры: `ContourPatternPicker` с двумя специально нарисованными SVG (сеткой «Порядок» и перекрывающимися фигурами «Хаос»). Настройка `settings_contour_pattern` использует `useLocalStorage`, включена в `APPEARANCE_KEYS` и доступна в `SettingsContext`. Два стабильных seeded набора в `BackIconsScene`: упорядоченный и хаотичный, пересекающийся. Превью и основной фон используют один паттерн.
- NeonCity: явно поднять `atNeonSkyline` над свечением/дорожной текстурой по `z-index`, сохранить различимость зданий и окон внизу и на высоких экранах.

Должны учитываться `prefers-reduced-motion`, безопасная область экрана и отсутствие двойного выбора фоновой плитки.

**фоновые сцены, анимация и сворачиваемая библиотека**

- Нижняя панель `BackgroundFullscreen` должна содержать две **рядом расположенные по центру** кнопки — круглую «Выйти» и `modulesenderInfo` с настройками/названием. Для обоих элементов устанавливать `pointer-events: auto`; у внешнего `PageBottom` они отключены, поэтому без переопределения плашка перестаёт нажиматься. Размеры и выравнивание проверять на ПК и iPhone.
- `supportsBackgroundMotion` разрешает движение только сценам с реальной управляемой CSS-анимацией. Для `landing`, `default`, `color`, пользовательских картинок и `sunset` переключатель и скорость **disabled**; искусственный `atBackgroundDrift` (zoom/pan) для неподвижных фонов не использовать. Переключение фонов не меняет состояние `movement`.
- В `art` у `SectionArt` есть собственные `artBob/artPulse/artSway/... ` keyframes, которые раньше работали даже при выключенном движении. Внутри `.atScene--art:not(.atScene--running)` явно отключать **все** CSS-анимации вложенных SVG через `animation: none !important`, не затрагивая независимые `SectionArt` на других страницах.

Оба режима и размер 0.5–1.5× должны работать в основной теме и в изолированном `BackgroundFullscreen` (`previewArtPattern` / `previewArtSize`), без записи в пользовательские настройки при предпросмотре.
- В `backgroundCatalog` «Рисунки AchieveTogether» находятся в «Основных». В `BackgroundLibrary` заголовки групп — кнопки с `aria-expanded` и сворачиваемым `hidden` содержимым; у SVG `LayoutGrid` в названиях контуров/рисунков `title` объясняет возможность настройки паттерна.

**реальный хаос в фоновых SVG**

- В `BackIconsScene` режим `order` сохраняет упорядоченную раскладку 54 иконок, а `chaos` создаёт **108 отдельных контурных SVG** с независимыми случайными `x/y` по всей площади, произвольными поворотами, разными размерами и невысокой прозрачностью. Для хаоса **нельзя** рассчитывать координаты от `row`/`column` даже со смещением: тогда снова возникает ровная сетка. Мягкое минимальное расстояние предотвращает отдельные чрезмерно плотные скопления, не выравнивая фигуры по рядам.
- В `BackgroundScene` режим `artPattern="order"` оставляет прежние четыре `SectionArt`. В `chaos` используются **8 разных иллюстраций**, случайно выбранных без повторов из всех 17 поддерживаемых `ArtTheme` (`SectionArt`); каждый экземпляр получает независимые `left/top/width/rotate`, их положение не привязано к фиксированным слотам. Сохраняются `artSize` и выключение внутренних анимаций через `atScene--art:not(.atScene--running)`.
- Случайный seed формируется **один раз при загрузке модуля**, а готовые позиции живут на уровне модуля. Поэтому переключение настроек и перерисовки React не двигают элементы хаотично каждый кадр, миниатюры и полноценный фон показывают **одинаковое** расположение. При следующей перезагрузке страницы композиция меняется.

### Цвета, состояния и оформление

**Критическое правило: градиент в hover и SVG**

В `docs/SCSS_GUIDE.md` есть **третья обязательная памятка**. При `linear-gradient(135deg, var(--accent), var(--grad))` **в любом состоянии, включая hover и active**, у поверхности `border: none`, у всего текста и вложенных SVG `color: var(--accent_text)`; вложенные SVG также должны иметь `color: var(--accent_text)`. Проверять специфичность общих hover и локальных CSS. Декоративный border только у поверхностей, за которыми виден фон приложения, кроме явных исключений.

**ОБЯЗАТЕЛЬНО: НЕЙТРАЛЬНАЯ КНОПКА НА ВИДИМОМ ФОНЕ ПРИЛОЖЕНИЯ ИМЕЕТ `border: 1px solid var(--block_border)`; УБИРАТЬ ЕГО ТОЛЬКО В ГРАДИЕНТНЫХ `:hover`, `:active`, `aria-expanded` ЧЕРЕЗ `border: none`. В ГРАДИЕНТНОМ СОСТОЯНИИ ВСЕ SVG И ТЕКСТ — `var(--accent_text)`. На внутренних `--mc` элементах декоративной границы нет.** Сверяться с четвёртой проверкой в `docs/SCSS_GUIDE.md`.

**правило обводок и градиентов (повторная обязательная фиксация)**

**Бордер добавляется только на внешнюю поверхность, за которой виден фон приложения, или когда он явно несёт смысл состояния (например, `border-color: var(--accent)` у просматриваемых обоев).** Внутри `--mc` и `--interact` нельзя размножать рамки на каждом вложенном контейнере или кнопке. **Любой активный градиент** `accent → grad` и `accent_highlight → grad_highlight` обязан иметь `border: none`, в том числе круглые кнопки с SVG и подтверждения. Нельзя накладывать полупрозрачный бордер поверх градиента: на краях получаются неверные цвета.

**Удаление — отдельное опасное действие, не акцентная кнопка:** `color: var(--notValid)`, `border: 1px solid var(--notValid)`, в hover/active — `background: var(--notValidBg)`; удаление с подтверждением через существующий `ConfirmAction`. Нейтральный элемент использует `--interact` без лишнего бордера. Повторять это правило при каждой новой правке SCSS, а не добавлять оформление наугад. Не добавлять `font-weight`.

**границы и градиенты (четвёртая фиксация)**

Это не рекомендация, а обязательное правило для каждого нового и изменённого элемента AT. **Нельзя добавлять бордер на кнопки и элементы с акцентным градиентом**: `background: linear-gradient(...var(--accent)...var(--grad)...)` или `linear-gradient(...var(--accent_highlight)...var(--grad_highlight)...)` ⇒ `border: none`. Для нейтральной поверхности внутри `--mc` / `--interact` не добавлять декоративный бордер; граница допустима у внешнего блока поверх фона сайта. **Исключение — действия удаления:** `color: var(--notValid)`, `border: 1px solid var(--notValid)`, `background: var(--interact)`; hover и active — `var(--notValidBg)`, без акцентного градиента. Пример: `.wallpaperStudioDelete`. Активный фон предпросмотра отмечать только `border-color: var(--accent)` на прозрачном резервном бордере миниатюры; реально применённый — отдельной SVG-галочкой. Не добавлять `font-weight`.

## Стили лениво загружаемых компонентов

Каждая страница из `React.lazy` и модалка из `ModuleMap` должна самостоятельно импортировать свои SCSS/CSS и стили общих компонентов, которыми пользуется. **Нельзя** рассчитывать, что стили появятся после посещения другой страницы, даже если в процессе обычной навигации это работает. Например, `AccInfo.tsx` сам загружает `AccInfo.scss`, а `HabitParticipantPicker.tsx` — стили `HabitChatMenu.scss` и `CreateChat.scss`. Переиспользуемые поля с `react-datepicker` импортируют также CSS библиотеки.

Перед коммитом выполнить `npm run check:lazy-styles`, `npm run build` и проверить прямые входы `/settings/acc`, `/info`, `/auth/qr` в новом окне без посещения других маршрутов. Не переносить все стили lazy-страниц в глобальный `App.scss`: это возвращает большой первоначальный CSS-бандл.


### Цвет текста на градиентных поверхностях

Для кнопок, карточек и выбранных вкладок с `background: linear-gradient(135deg, var(--accent), var(--grad))` устанавливать `color: var(--inner_text)` для текста и SVG, в том числе на `hover`/`active`. Если у того же элемента в обычном состоянии `background: var(--mc)` или `var(--interact)`, оставлять существующий цвет текста без изменений. Не использовать `--accent_text` поверх акцентного градиента.


Для сплошных фонов `background: var(--accent)`, `background-color: var(--accent)` и `background-color: var(--darker_accent)` действует то же правило: текст и иконки — `var(--inner_text)`. На нейтральной поверхности использовать обычный цвет; проверять вложенные подписи и состояния hover/active. CI проверяет `tests/accent-text-contrast.test.mjs`.

## Обязательная проверка градиента, рамки и SVG

Во всех состояниях (`:hover`, `:active`, `[aria-expanded="true"]`, selected, `:focus-visible`, disabled) при `background: linear-gradient(135deg, var(--accent), var(--grad))` декоративный `border` должен быть `none`, а текст, вложенные span, svg, path и компоненты — цвета `var(--accent_text)`. Проверять каждое состояние, а не только обычное. Нейтральное стеклянное окно может сохранять штатную рамку Blackout. На нейтральной кнопке допускается `border: 1px solid var(--block_border)` и `background: var(--interact)` с акцентным SVG. При переходе к градиенту рамка снимается и текст с SVG получают `var(--accent_text)`.
